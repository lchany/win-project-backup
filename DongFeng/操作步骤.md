# NPU 性能优化操作步骤

## 记录规则

- 本文件记录本项目从计划、代码审计、验证、基线、profile、优化到回归的每一个逻辑操作步骤。
- 每一步必须包含：目的、原因、操作指令、观察现象、现象说明、下一步。
- 操作指令中的远程地址、用户、凭据和共享目录一律脱敏；共享目录统一写作 `{{SHARED}}`。
- 从 2026-08-11 用户补充该规则后，执行新操作前先登记目的/原因/预定指令，执行后立即补齐结果；此前步骤按终端与规划文件记录回填。
- 轮询同一长任务的命令按一个逻辑步骤归档，并记录关键状态变化，不逐次复制内容完全相同的轮询输出。
- 禁止将远端服务器上的数据、数据集、日志、profile、checkpoint、模型或训练产物拉取/同步到本地；禁止对这些内容使用 `remote_sync.py pull`、`scp`、`sftp get` 等下载操作。所有原始数据分析必须在远端服务器/容器内完成，本地仅记录经远程命令返回并已脱敏的必要摘要、指标和结论。向远端推送经审查的临时代码不属于拉取，但仍须逐步记录。

## STEP-004：审计随机性固定、调试代码与 CPU fallback

- 目的：确认此前固定随机性是否全部还原，并避免提前混入算子优化。
- 原因：随机性移除必须形成唯一独立提交，CPU fallback 要留到性能证据和成熟算子调研完成后处理。
- 操作指令：使用 `git show`、`git diff`、`git grep` 检索 `seed`、`manual_seed`、`PYTHONHASHSEED`、`HCCL_DETERMINISTIC`、`DBG_NPU`、`RESET_DEBUG`、`SAMPLER_DEBUG`、`.cpu()`、`.numpy()` 等模式，并逐文件与 `f189414^` 对比。
- 观察现象：固定值 666、全局 Python/NumPy/PyTorch/torch_npu seed、确定性环境和禁用数据增强/打乱已删除；但 SeTa `if True`、多个 sampler/debug 输出、detector 指纹日志和单卡启动仍未完整还原。MSDA CPU fallback 本体来自更早提交，不属于本阶段。
- 现象说明：原随机性移除提交需要补齐 7 个文件的还原，但不能在此提交中替换 MSDA 算子。
- 下一步：补齐随机性/调试还原并做静态检查。

## STEP-012：执行第 1 次 8 卡普通计时基线

- 目的：测量冷启动、稳态 step、周期性长尾、显存和端到端吞吐。
- 原因：profiler 有额外开销，普通计时必须单独完成。
- 操作指令：基于 `tools/ddp_train.sh`，使用设备 0-7、端口 29631、全局 batch 8、30 步窗口；每 5 秒用 `npu-smi` 和 `ps` 采集资源。
- 观察现象：首步 213.604 秒；第 11/21 步分别 271.366/271.606 秒；排除首步和周期空洞后中位 3.038 秒、P95 6.485 秒；30 步均值 28.532 秒，端到端吞吐 0.2804 sample/s；最大记录显存 5067 MB；无 fatal。
- 现象说明：纯 NPU 稳态计算约 3 秒，但每 10 步一次约 271 秒的 host 空洞主导总体吞吐。
- 下一步：在空洞期间检查 NPU、CPU 和主线程栈，并用独立运行复现。

## STEP-013：对周期性 host 空洞做只读现场诊断

- 目的：判断长尾来自 NPU、通信、I/O 还是 host 计算，并为 profiler 选择窗口。
- 原因：第 1 次基线在第 10 步后长时间无新日志，不能仅凭经验修改代码。
- 操作指令：空洞期间执行 `npu-smi info`、`ps -eo pid,pcpu,stat,wchan,cmd`；用 `gdb -p <rank0-pid>` 只读抓取主线程 C 栈。
- 观察现象：8 张 NPU AICore 为 0%，8 个主 rank 各占约 100% host CPU；主线程先位于 NumPy `FLOAT_multiply`，再次采样位于 OpenBLAS `dgemm_kernel_ARMV8SVE`；无 HCCL/异常日志。
- 现象说明：周期空洞是同步 host NumPy/BLAS 计算，不是 NPU kernel 或 HCCL 卡死；仍需 profiler/Python 调用链定位具体业务函数。
- 下一步：用第 2、3 次完全相同基线确认复现性。

## STEP-016：汇总三次普通基线

- 目的：形成后续所有优化的统一 Before 数据。
- 原因：需要同时报告真实端到端吞吐和排除周期空洞后的纯稳态性能。
- 操作指令：解析三份 `launcher.log` 中 iteration、time、memory、loss、grad_norm，计算 pooled median、P95、均值、CV 和吞吐；清理每次运行生成物并确认工作树干净。
- 观察现象：90 个 step 的总体中位 3.216 秒、P95 256.672 秒、均值 28.932 秒，端到端吞吐 0.2765 sample/s；81 个非冷启动/非周期 step 中位 3.186 秒、P95 7.074 秒，理想稳态吞吐 2.5110 sample/s；6 次周期空洞中位 271.486 秒、P95 280.307 秒、CV 3.81%；三次 run 均值的 CV 为 3.39%；冷启动中位 217.658 秒。
- 现象说明：约 10 倍的端到端吞吐损失主要来自每 10 步一次的 host NumPy/BLAS 阶段，优先级高于常规 3 秒 NPU step 内的小算子优化。
- 下一步：先把本文件补齐并写入规划进度，然后设计能覆盖第 10→11 步空洞和正常稳态 step 的 8 卡 profiler 采集。

## STEP-030：实机验证 NPU FP32 QR/eigh 成熟算子候选

- 目的：确认 Ascend 原生 `aclnnLinalgQr` 在当前 910/CANN 8.3.RC1/TorchNPU 2.7.1 上对本项目矩阵 shape 的功能、精度与速度，并判断 `eigh` 是否存在可用 NPU 路径。

- 操作指令：先用 rank0 profiler DB 的 `PYTORCH_API.inputShapes + STRING_IDS` 远端聚合 Step 10 的 551 次 `aten::linalg_qr` shape/次数，只返回维度摘要；检查 NPU 0–7 是否有计算进程，若有则按用户授权精确核验并停止占用程序。随后在 `mapqr` 容器、单个空闲 NPU 上运行独立 Python 微基准：用确定性公式构造各唯一 shape 的对称正定 FP32 矩阵与正交初始 Q（不设置随机种子、不读取业务 tensor），分别执行设备端 `m@Q`、argsort、`torch.linalg.qr` 和 `torch.linalg.eigh`；同步计时 warmup/重复，计算 `||Q^TQ-I||`、`||QR-A||/||A||`、与 CPU FP64 结果按列符号对齐后的相对误差，并通过轻量 TorchNPU profiler/算子日志确认 QR 实际走 ACLNN/NPU 而非 AICPU/CPU。所有脚本与产物只放远端诊断目录，本地仅接收脱敏聚合结果，严禁拉取原始数据。

## STEP-031：筛选大矩阵与 eigh fallback 的成熟算法级替代

- 目的：为 2560/5120 AICPU QR 性能倒挂和初始化 `eigh` CPU fallback 找到成熟、语义可解释的方案，并确定第一版业务 A/B 的最小改动组合。
- 原因：单纯设备端 QR 只约 1.41x，不能解决主瓶颈；但降低维度阈值或改变初始化会影响优化器语义，必须由 SOAP/Distributed Shampoo 的成熟设计与项目现状共同支撑。
- 操作指令：远端只读审计当前 `soap.py` 的 `get_fast_QR`、`get_orthogonal_matrix`、`get_orthogonal_matrix_QR`、`max_precond_dim` 分支、配置传参和相关 git 历史；从 profile 调用栈/shape 统计判断 2560/5120 轴是否可由阈值形成一侧 SOAP。联网阅读 SOAP 论文/原作者说明以及 Meta/Facebook Research Distributed Shampoo 的 `DefaultSOAPConfig`、QR eigenvector 初始化、precision、large-dimension blocking/threshold 与 Newton-Schulz 配置源码/文档。对候选按算法等价性、当前 PyTorch/NPU 可用性、预计周期耗时、loss 风险和实现复杂度排序；不上传项目代码、不下载远端数据、不修改业务代码。
- 观察现象：第一次用 `git ls-files '*soap.py' | head -1` 误命中了名称含 `fastsoap.py` 的配置文件；改为锚定 `(^|/)soap\.py$` 后确认仓库有根目录副本和实际由 `projects/mmdet3d_plugin/optimizers/__init__.py` 注册的插件实现，两者 SHA-256 不同，当前训练使用后者。一次带 `set -e` 的 `cmp` 因两个副本不同而提前退出，去掉提前退出后完成审计。实际 SOAP 默认 `max_precond_dim=10000`，当前 config 只传 `precondition_frequency=10`，因此 2560/5120 均进入预条件。对超过阈值的轴，`init_preconditioner` 写入空列表，`update_preconditioner` 不构造该轴的二阶矩阵，`project/project_back` 只做维度轮转，等价于该轴使用单位旋转；这已经是项目内置能力。初始化 `get_orthogonal_matrix` 对 NPU 显式转 CPU FP64 `eigh`，周期更新则把 `m/Q` 转 CPU FP64 做 `Q^T m Q`、排序、`mQ` 和 QR；这些 fallback 均由 `dd23198` QR。Meta/Facebook Research 当前 `DefaultSOAPConfig` 使用 `QREigendecompositionConfig(max_iterations=1)`；其状态源码先把 eigenvectors 初始化为设备上的单位阵，再把该单位阵作为 estimate 交给 QR 算法，因此“单位阵初始化 + 首次也执行一轮设备 QR”是成熟实现，可彻底避开初始化 `eigh`。Meta 还提供 `ignored_basis_change_dims`、分块/维度合并、矩阵精度和自适应 tolerance，但当前包要求 PyTorch>=2.8/Python>=3.12 且仅声明 CUDA 测试，不能整包替换当前环境。远端只构建模型结构、不读数据集/权重，得到 701 个可训练参数；实际大轴集中在 4 层 lane3d attention：4 个 `(2560,5120)` 权重、4 个 `(256,2560)` 权重及若干不参与 1D 预条件的 bias，另有 `(15360,256)` embedding 在本次 profile 没产生 QR。该映射精确解释 profile 的 2560×8、5120×4：`(2560,5120)` 各贡献一个 2560 和一个 5120，`(256,2560)` 各再贡献一个 2560。故简单设 `max_precond_dim=1024/2048` 会让 `(2560,5120)` 两侧都不旋转，并非论文的一侧 SOAP；设为 2560 又会为 `(256,2560)` 多保留不必要的 2560 大侧。按实机微基准加权，若仅对含大轴的 2D 参数采用论文 one-sided、其余保持双侧，则消除 4 次 5120 和 4 次不必要的 2560，只保留 `(2560,5120)` 的 4 `https://proceedings.iclr.cc/paper_files/paper/2025/file/e988664070e9591f93fdcf605f7dc623-Paper-Conference.pdf`、Meta 类型配置 `https://github.com/facebookresearch/optimizers/blob/main/distributed_shampoo/shampoo_types.py`、Meta QR 配置/算法 `https://github.com/facebookresearch/optimizers/blob/main/distributed_shampoo/preconditioner/matrix_functions_types.py` 与 `matrix_functions.py`、Meta identity 状态初始化 `https://github.com/facebookresearch/optimizers/blob/main/distributed_shampoo/preconditioner/shampoo_preconditioner_list.py`、SOAP 原作者实现 `https://github.com/nikhilvyas/SOAP/blob/main/soap.py`。
- 现象说明：第一版最有证据的组合不是机械降低全局阈值，也不是把所有矩阵直接迁到 AICPU QR，而是：沿用 SOAP/Meta 的一轮 power-iteration+QR 语义，把 Q 初始为设备单位阵以消除 `eigh` fallback；周期路径全部保持 NPU FP32；仅对出现 >1024 大轴的 2D 权重使用论文 one-sided 规则，保留较小轴、跳过较大轴。它能消除全部 CPU fallback，并避开 5120 AICPU 性能倒挂，同时对绝大多数参数保持现有双侧 SOAP。风险排序为：①该“只对大轴启用 one-sided”的混合策略仍会改变 8 个大权重的优化器语义，必须做 loss/状态 A/B；②2560 AICPU QR 仍约 4 秒/次，是剩余主要周期成本；③Meta 的整包实现不兼容当前运行时，只能移植已核实的算法模式，不能直接引入依赖。候选优先级：A=混合 one-sided + identity/QR 初始化 + NPU FP32（首选）；B=成熟分块 Shampoo/SOAP（语义更接近双侧但改动和状态迁移大，作为 A 不通过时备选）；C=全局阈值 1024/2048（会使 `(2560,5120)` 完全退化为无旋转，风险更高）；D=Newton-Schulz/子空间 QR（当前成熟实现面向谱下降或 2026 新研究，不是 SOAP eigenbasis 的等价替换，暂不采用）；E=只提高频率（不能消除 fallback，且论文已报告频率升高会降低性能）。
- 下一步：先登记 STEP-032，在不修改受版本控制业务代码的前提下建立可复现的 SOAP 函数级 A/B：用真实 shape 组合和确定性合成状态验证“identity 首次 QR、混合 one-sided、全 NPU FP32”对 Q 正交性、投影/回投、`exp_avg_sq` 维度重排及周期耗时；同时核对 rank 间结果差异。函数级门禁通过后，再进入最小业务补丁与 8 卡短训练 A/B；若 2560 仍不可接受，再评估成熟分块方案。
